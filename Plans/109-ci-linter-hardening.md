# План 109 — Поэтапное ужесточение блокирующих CI-линтеров

**Статус:** ⬜ Проект

**Дата фиксации baseline:** 2026-07-27

**Родитель:** [план 56, этап 2](56-techdebt-ci-observability.md#этап-2--golangci-lint)

**Отправная точка:** после включения `staticcheck` в блокирующий CI (PR #427).

## Контекст

CI запускает `golangci-lint` версии `v2.11.4`. В `.golangci.yml` сейчас включены
`govet`, `ineffassign` и `staticcheck`; оставшаяся очередь — `bodyclose`, `unused`,
`errcheck` и `gosec`.

Полный baseline получен закреплённой CI-версией без стандартного ограничения числа
однотипных сообщений:

```bash
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.11.4 run \
  --enable-only=<linter> \
  --max-issues-per-linter=0 \
  --max-same-issues=0 \
  ./...
```

| Линтер | Всего | Production | Tests | Что важно |
|---|---:|---:|---:|---|
| `bodyclose` | 0 | 0 | 0 | Можно включить сразу отдельным минимальным PR |
| `unused` | 29 | 26 | 3 | Перед удалением проверить build tags и OS-specific код |
| `errcheck` | 968 | 703 | 265 | Нужна разбивка по риску, а не массовые `_ =`/`nolint` |
| `gosec` | 1522 | — | — | 577 — `G104`, пересекающийся с `errcheck`; самостоятельных срабатываний до повторной проверки — 945 |

Распределение текущего `gosec` baseline по правилам:

|---|---:|---|---:|
| `G104` | 577 | `G120` | 245 |

| `G203` | 27 | `G115` | 25 |

Baseline — снимок объёма работ, а не разрешение сохранять эти нарушения.

## Цель

Включить все четыре линтера в обычный блокирующий `golangci-lint` job так, чтобы:

- полный запуск каждого линтера возвращал `0 issues`;
- новые нарушения блокировали каждый PR;
- реальные ошибки исправлялись с сохранением или усилением fail-closed поведения;
- исключения были точечными, проверяемыми и документировали причину;
- обновление версии `golangci-lint` оставалось отдельным изменением с новым аудитом.

## Не входит в план

- одновременное включение дополнительных style/complexity-линтеров;
- массовое форматирование и рефакторинг несвязанных модулей;
- широкие `exclude-dirs`, регулярные выражения на пакеты или baseline-файлы,
  скрывающие новые нарушения;
- механическая замена каждой проигнорированной ошибки на `_ =`;
- обновление Go, зависимостей или версии `golangci-lint` в тех же PR.

## Порядок реализации

Порядок фиксирован: `bodyclose` → `unused` → `errcheck` → `gosec`.
Сначала включается уже чистый линтер, затем удаляется небольшой объём мёртвого кода.
`errcheck` идёт до `gosec`, потому что закрывает значительную часть `G104` и уменьшает
security-baseline до содержательно разбираемого объёма.

### PR 109A — включить `bodyclose`

1. Добавить `bodyclose` в `linters.enable` в `.golangci.yml`.
2. Удалить его из комментария с очередью.
3. Подтвердить `0 issues` полным запуском с unlimited-флагами.
4. Дождаться всех обязательных CI checks и влить PR отдельно от остальных этапов.

**Критерий готовности:** `bodyclose` блокирует merge, исключений нет.

### PR 109B — закрыть и включить `unused`

1. Получить полный список 29 находок и распределить его по пакетам.
2. Для каждой декларации проверить:
   - build tags (`integration`, `webview` и другие);
   - OS-specific файлы и entry points утилит;
   - использование через генерацию, шаблоны и тестовые helpers.
3. Удалять только доказанно мёртвый код; связанный крупный рефакторинг вынести отдельно.
4. Запустить обычную сборку/тесты и доступные tag-specific compile checks.
5. Добавить `unused` в `.golangci.yml` только после `0 issues`.

**Критерий готовности:** `unused` блокирует merge; нужный tagged-код не удалён.

### PR 109C — защита от роста незакрытого baseline

До начала серии `errcheck`/`gosec` добавить временный blocking job для нарушений,
появившихся после merge-base ветки с актуальным `origin/main`
(`--new-from-merge-base=origin/main`). Текущий lint job использует shallow checkout,
поэтому для этой проверки нужно явно установить `fetch-depth: 0`.

Этот job — только предохранитель на период миграции: он не заменяет полный прогон,
не считается закрытием baseline и удаляется после включения обоих линтеров обычным
способом. Если режим `new-from-merge-base` неустойчиво классифицирует находки в
текущем workflow, вместо ослабления проверки PR должен сначала закрыть линтер целиком.

**Критерий готовности:** новые нарушения в изменённых строках блокируются, старые
не замаскированы исключениями в `.golangci.yml`.

### PR 109D–109G — закрыть `errcheck`

968 находок нельзя исправлять одним механическим PR. Серия делится по поведению:

1. **Критичные production write paths:** транзакции, `Exec`/`Scan`, auth/session,
   backup/restore, запись файлов, сетевые запросы и команды ОС. Ошибка должна
   возвращаться вызывающему коду, откатывать операцию или переводить её в явно
   безопасное состояние.
2. **HTTP/UI/CLI output:** `Encode`, `Write`, templates и stdout/stderr. До начала
   ответа ошибку можно вернуть; после частичной записи — зафиксировать структурным
   логом и прекратить дальнейшую запись.
3. **Cleanup и best-effort операции:** `Close`, `Rollback`, удаление временных файлов,
   фоновые housekeeping-операции. Ошибки финализации записи обязаны влиять на
   результат; вторичные cleanup-ошибки объединять с основной либо логировать.
4. **Тесты и инструменты:** setup/assertion errors проверять через `require`/`t.Fatal`;
   cleanup — через helper/`t.Cleanup` с диагностикой. Исправления тестов не должны
   превращаться в production suppressions.

Один PR должен охватывать один класс поведения или небольшой набор связанных
пакетов. Для практически неизбежного игнорирования допустим только точечный комментарий
вида `//nolint:errcheck -- <конкретная причина>` на той же строке. Голые `_ =`,
package-wide исключения и подавление `fmt`/`io`/`sql` целиком запрещены.

Финальный PR этапа повторно замеряет весь репозиторий после rebase, получает
`0 issues`, включает `errcheck` в `.golangci.yml` и обновляет baseline в этом плане.

**Критерий готовности:** `errcheck` блокирует merge; в critical paths нет молча
проглоченных ошибок; временный changed-code gate остаётся для `gosec`.

### PR 109H–109J — разобрать и включить `gosec`

1. После закрытия `errcheck` заново снять baseline: значение 1522 устареет из-за
   исчезновения `G104`.
2. Сначала разобрать правила с возможным внешним воздействием: hardcoded secrets,
   запуск команд, path traversal/file inclusion, taint-потоки, слабая криптография
   и неконтролируемое потребление ресурсов.
3. Затем проверить права файлов/каталогов, integer conversions, random в load-test
   утилитах и остальные правила с учётом реальной trust boundary.
4. Реальные проблемы закрывать тестом на соответствующую границу: traversal,
   SSRF/tainted input, command arguments, permissions или overflow.
5. False positive разрешён только как
   `//nolint:gosec -- Gxxx: <почему вход доверенный или какой guard это гарантирует>`.
   Подавление целого правила или директории не допускается.
6. После `0 issues` включить `gosec` в `.golangci.yml`, удалить временный
   changed-code job и обновить итоговый baseline/статус плана.

**Критерий готовности:** `gosec` блокирует merge, каждое оставшееся подавление
указывает правило и проверяемое основание.

## Общий PR-gate

Для каждого PR серии обязательны:

```bash
git diff --check
go test ./...
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.11.4 run ./...
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.11.4 run \
  --enable-only=<целевой-linter> \
  --max-issues-per-linter=0 \
  --max-same-issues=0 \
  ./...
```

Дополнительно:

- `go test -race ./...` — обязательно через CI; локально для затронутых
  конкурентных пакетов;
- integration/tag-specific проверки — если менялись storage, auth, network,
  backup/restore или tagged-код;
- все обязательные GitHub checks должны быть зелёными до merge;
- PR нельзя сливать при неполном/обрезанном выводе целевого линтера.

## Definition of Done

- [ ] `bodyclose`, `unused`, `errcheck`, `gosec` перечислены в `linters.enable`.
- [ ] Каждый полный unlimited-запуск возвращает `0 issues`.
- [ ] Обычный lint job блокирует новые нарушения на любом PR.
- [ ] Временный `--new-from-merge-base` gate удалён.
- [ ] Нет широких исключений и безымянных `nolint`.
- [ ] Поведенческие исправления ошибок и security-находок покрыты тестами.
- [ ] `.golangci.yml`, план 56, этот план и `Plans/README.md` отражают итоговый факт.

## Риски и правила отката

- Изменение обработки ошибки способно поменять публичное поведение. Такой PR должен
  описывать прежний и новый контракт и иметь regression test.
- Ошибка `Close` у writer/archive/database может быть основной, а не вторичной:
  её нельзя автоматически переводить в лог.
- После обновления анализатора могут появиться новые правила. Версию сначала
  закрепить отдельным PR, снять новый unlimited-baseline и только затем исправлять.
- При ложном срабатывании не отключать уже блокирующий линтер: сузить guard или
  добавить точечное обоснованное подавление.
